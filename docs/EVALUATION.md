# Evaluation

The harness is the primary deliverable of this repository, not a test folder.

`python -m evals.runner` runs all five layers, prints a scorecard, and exits
non-zero if any gate fails. CI runs it on every pull request, so a regression
cannot merge.

## Why gates, not dashboards

A metric that is reported but not enforced drifts. The five layers are release
gates: below threshold, the build fails. That is the difference between measuring
quality and having it.

## The five layers

### 1. retrieval_quality — gate 0.90 recall@5

Does the right chunk surface at all? Recall@k and MRR against labeled
query-to-chunk pairs.

Gate is 0.90, a real threshold rather than 1.0, because recall genuinely trades
against corpus size and this is a ranking quality metric, not a correctness
guarantee.

### 2. scope_precision — gate 1.00

Can a wrong-scope chunk surface? Distinct from layer 1, and a system can pass one
while failing the other.

For each adversarial cross-year case, retrieval must return the expected chunk and
must return **zero** chunks from any other tax year. Gate is absolute: one
wrong-year retrieval means the architectural guarantee does not hold, and the
guarantee is the entire claim of the project.

The adversarial corpus is written so 2024 and 2025 passages for each provision are
near-identical except the figure. That is not artificial; it is how tax
publications actually read year over year.

### 3. numeric_correctness — gate 1.00

25 golden cases, exact match, no tolerance. A tax figure is either right or wrong,
and a tolerance band is a way of not noticing which.

Every expected value was computed by hand from the cited rule and then encoded.
That ordering is load-bearing: an expectation generated by the code under test
proves only that the code is self-consistent.

Three case pairs are deliberately built to isolate one variable:

- `mortgage-2024-limit-binding` vs `mortgage-2024-grandfathered` — identical
  inputs except origination date. 30,000 vs 40,000.
- `sli-2024-fully-phased-out` vs `sli-2025-same-magi-different-year` — identical
  taxpayer, adjacent years. 0.00 vs 166.67.
- `compare-2024-standard-wins` vs `compare-2025-itemizing-wins-on-salt-change` —
  identical taxpayer, adjacent years. The raised 2025 SALT cap flips them from
  standard to itemizing.

That second pair is the clearest single demonstration of why tax year cannot be a
soft signal: the same person's deduction goes from zero to nonzero on a threshold
change alone.

### 4. groundedness — gate 1.00

Every dollar figure in a produced answer must appear in the computation trail.
Calls the same `selfcheck_node` the runtime uses, deliberately, so the eval and the
guard cannot disagree.

Includes negative controls: answers with an invented figure and with a missing tax
year, which the guard must **reject**. Passing means the check correctly refused. A
layer that silently stopped working shows up as a failure rather than as a
suspiciously perfect score.

### 5. escalation_preference — gate 1.00

Under-specified and out-of-scope questions run through real routing logic and must
produce a clarification or an escalation, not an answer.

This layer is what keeps the system honest as coverage grows. Without it, every
future improvement creates pressure to answer more questions and the escalation
path quietly erodes.

It earned its place on the first run by catching two genuine defects: the scope
node resolved "California standard deduction for 2025" to a federal answer, and
resolved tax year 2027 despite no rule data existing. Neither would have been
caught by the unit tests.

## The ablation

`python -m evals.ablation`

Naive retrieval versus scoped retrieval. Same corpus, same queries, same scoring
function. The only difference is whether resolved scope enters as a hard pre-filter
or not at all.

| metric | naive | scoped |
|---|---|---|
| wrong tax year at rank 1 | 6 / 12 | 0 / 12 |
| wrong-year chunks in top 5 | 30 | 0 |
| precision@1 | 41.7% | 100% |

`test_ablation_shows_naive_retrieval_failing` asserts that naive retrieval still
fails on this corpus. If it ever stops failing, the adversarial set has become too
easy and needs to be made harder. That is a maintenance signal, not a flaky test.

## Running with no API key

Every layer runs on `pydantic` and `pyyaml` alone. No model download, no API key,
no network. That is a deliberate constraint for a public repository: a reader who
cannot run the evals cannot check the claims, and unverifiable claims in a README
are just assertions.

## Adding a case

- **Numeric**: add a `GoldenCase` to `evals/datasets/golden_profiles.py` with the
  expected value computed by hand and a `rationale` explaining the derivation.
- **Cross-year**: add a `CrossYearCase` with `expected_chunk_ids` and
  `forbidden_chunk_ids`, plus fixture chunks for both years if the provision is new.
- **Escalation**: add an `EscalationCase` with the expected behavior and a `why`
  that states what would go wrong if the system answered.

The `why` and `rationale` fields are not documentation. They appear in failure
output, which is when someone most needs to know what the case was protecting.
